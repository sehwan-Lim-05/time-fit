# 매출 분석 UI·UX 및 데이터 보완 기획

작성일: 2026-09-23  
검토 기준: 운영 화면 캡처, `origin/main`의 `WeeklyFeedback`, `weeklySales`, `operations-feedback` API 구현

## 1. 결론

현재 화면은 지난주와 전주를 같은 요일 구성으로 비교하고, 완료 매출·완료 주문·주문당 금액을 한 화면에 제공한다는 점은 좋다. 다만 다음 두 문제가 크다.

1. 첫 화면의 큰 여백과 중복 제목 때문에 핵심 차트가 첫 화면 아래로 밀린다.
2. 최근 수집 시각은 보이지만, 선택 기간 전체가 POS 원본 기준으로 완전히 수집됐는지와 이후 취소·정정이 반영됐는지를 사용자가 판별하기 어렵다.

따라서 1차 개선 목표는 “예쁜 분석 화면”이 아니라 아래 세 가지다.

- 5초 안에 이번 주 결과와 전주 대비 원인을 이해한다.
- 숫자의 기준 시각, 수집 범위, 완결 여부를 바로 확인한다.
- 이상한 날짜나 메뉴를 눌러 원인 주문까지 추적한다.

## 2. 현재 화면 평가

### 유지할 강점

- 진행 중인 주가 아니라 완료된 월~일을 기본 비교한다.
- 동일한 7개 요일끼리 비교해 요일 구성 왜곡을 줄인다.
- 방문객 정보가 없으므로 객단가 대신 `주문당 금액`을 사용한다.
- 완료 주문만 매출로 계산하며 비교 데이터가 불완전하면 증감을 숨긴다.
- 일별 매출과 메뉴 판매를 분리해 정보량을 제어한다.
- 모바일에서 KPI를 한 열로 바꾸는 기본 반응형 구조가 있다.

### 데이터 문제

#### 2.1 기간 완결성 판단

현재 `weeklySales`는 다음 조건을 주로 사용한다.

- 일별 캐시의 `order_count`와 저장된 원주문 수가 같은지 확인
- 연결의 `last_synced_at`이 선택 주 종료 이후인지 확인

이는 타임핏 내부의 원주문과 캐시가 서로 일치한다는 것은 보장하지만, POS 원본의 해당 기간 전체가 수집됐다는 사실을 충분히 증명하지 못한다. 최근 동기화가 다른 기간만 조회했어도 `last_synced_at`은 새 값일 수 있다.

보완 원칙:

- 동기화 성공 시각이 아니라 실제 `window_from`, `window_to`, 페이지 완주 여부를 기간별로 저장한다.
- 화면은 선택 주와 비교 주가 모두 수집 범위에 포함된 경우에만 `마감 완료`로 표시한다.
- 내부 원주문 합계와 일별 캐시 합계도 별도로 대조한다.

#### 2.2 오후 10시 기준과 후속 정정

오후 10시 수집은 “기준 시각”이며, 늦게 반영된 주문·취소·상태 변경 때문에 이후 값이 바뀔 수 있다. 따라서 상태를 이분법으로 처리하지 않는다.

- `수집 대기`: 해당 날짜 오후 10시 이전
- `1차 수집 완료`: 오후 10시 기준 수집 성공
- `마감 확정`: 다음 재수집에서 페이지 완주 및 원본/캐시 대조 완료
- `재집계됨`: 마감 후 주문·취소·금액이 변경됨
- `수집 지연/불완전`: 오류, 페이지 상한, 범위 미포함, 합계 불일치

주간 분석 기본값은 7일 모두 `마감 확정`된 주만 사용한다. 그렇지 않으면 합계는 보여줄 수 있지만 전주 대비 백분율과 자동 인사이트는 숨긴다.

#### 2.3 매출 정의

화면과 다운로드에서 다음 용어를 고정한다.

- 완료 매출: 상태가 완료인 주문의 `total_amount` 합계
- 완료 주문: 상태가 완료인 주문 수
- 취소 주문: 취소 상태 주문 수
- 주문당 금액: 완료 매출 / 완료 주문
- 메뉴 판매 수량: 완료 주문의 유료 품목 수량
- 메뉴 판매액: 주문 할인·옵션·취소 배부 규칙을 확정하기 전에는 참고값으로 표시

`매출`, `순매출`, `결제액`, `주문액`을 혼용하지 않는다. 지출·순익 화면과 연결할 때도 동일한 완료 매출 정의를 사용한다.

#### 2.4 메뉴 식별

현재 집계는 메뉴 이름을 키로 사용한다. 이름 변경, 동일 이름, 옵션 표기 차이로 서로 다른 메뉴가 합쳐질 수 있다.

- 1순위: POS 메뉴 코드 또는 품목 ID
- 2순위: 정규화된 메뉴명 + 카테고리
- 화면 표시: 현재 이름
- 이름 변경 이력은 같은 메뉴 코드로 연결
- 무료 옵션과 증정 메뉴는 유료 메뉴 순위에서 제외하되 별도 옵션 분석 후보로 보존

## 3. 목표 화면 구조

### 3.1 상단 헤더

한 줄에 다음을 배치한다.

- 제목: `매출 분석`
- 기간: `2026.09.14 월 – 09.20 일`
- 비교 기준: `전주 동일 요일 대비`
- 상태 칩: `마감 완료`, `수집 지연`, `재집계됨` 중 하나
- 행동: `이전 주`, `다음 주`, `최근 마감 주`, `최신 매출 동기화`

보조 줄:

`POS 수집 완료 09.22 22:24 · 수집 범위 09.07 00:00–09.20 23:59 · 14일 모두 대조 완료`

### 3.2 KPI

첫 화면에 4개만 둔다.

1. 완료 매출
2. 완료 주문
3. 주문당 금액
4. 취소 주문 또는 취소 금액

각 KPI는 `현재값 / 절대 차이 / 비율 차이 / 비교값`을 가진다.

예시:

```text
완료 매출
30,530,900원
▼ 948,200원 · 3.0%
전주 31,479,100원
```

비교값이 0이면 퍼센트를 만들지 않고 `전주 기준값 없음 · +1,240,000원`으로 표시한다.

### 3.3 핵심 인사이트

자동 문장은 사실 기반 조합만 허용한다.

- `매출은 3.0% 감소했습니다. 주문 수 -3.6%, 주문당 금액 +0.6%입니다.`
- `매출 감소의 주된 수치 요인은 주문 수 감소입니다.`
- 원인, 수요, 직원 성과, 날씨 효과는 근거 데이터 없이 추정하지 않는다.

### 3.4 일별 비교

- 기본: 7일 쌍대 막대 또는 선 그래프
- 진한색: 선택 주, 옅은색: 비교 주
- 날짜별로 매출, 주문 수, 주문당 금액을 툴팁에 제공
- `매출 / 주문 수 / 주문당 금액` 보기 전환
- 가장 큰 증가일과 감소일 표시
- 날짜 클릭 시 일자 상세 드로어 표시

일자 상세 드로어:

- 완료 매출, 완료/취소 주문, 주문당 금액
- 시간대별 매출
- 상위 메뉴 5개
- 해당 날짜 주문 목록으로 이동
- 데이터 상태와 마지막 수집 시각

### 3.5 메뉴 판매

기본 열:

| 순위 | 메뉴 | 카테고리 | 판매 수량 | 주문 수 | 판매액 | 매출 비중 | 전주 증감 |
|---|---|---|---:|---:|---:|---:|---:|

기능:

- 판매액순/수량순/증가순/감소순 정렬
- 카테고리 필터와 메뉴 검색
- 상위 10개 기본, 전체 보기
- 메뉴 클릭 시 날짜별 판매 추이
- 메뉴 코드가 없는 데이터는 `이름 기준 집계` 안내

### 3.6 데이터 상태 패널

기본은 접고, 문제가 있을 때 자동으로 펼친다.

- 선택 주 수집 범위
- 비교 주 수집 범위
- 성공/실패 시각
- 페이지 완주 여부
- 원주문/일별 캐시 대조 결과
- 수집 이후 정정 주문 수
- 오류 발생 시 재시도 행동

## 5. 저장 구조 보완

권장 신규 이력 테이블: `timefit_user_sales_sync_runs`

필드:

- `organization_id`, `merchant_id`
- `started_at`, `completed_at`
- `window_from`, `window_to`
- `requested_mode`
- `pages_fetched`, `orders_received`
- `page_complete`
- `summary_refresh_completed`
- `status`, `error_code`, `error_message`
- `source_checksum` 또는 기간 합계 스냅샷

일별 집계에는 다음을 보강한다.

- `completed_order_count`
- `cancelled_order_count`
- `completed_amount`
- `last_source_synced_at`
- `finalization_status`
- `revision_number`

동기화는 성공한 범위를 덮어쓰는 것이 아니라 실행 이력을 남긴 뒤 일별 집계를 갱신한다. 부분 실패 시 이전 확정값은 유지하고 상태만 `불완전`으로 표시한다.

## 6. 개발 순서

### 1차 — 데이터 신뢰성 P0

- 동기화 실행 이력과 실제 수집 범위 저장
- 페이지 완주 여부 저장
- 원주문/일별 캐시 합계 대조
- 주간 API에 상태·범위·정정 여부 추가
- 과거 선택 주를 최근 수집 시각만으로 완료 처리하는 조건 제거
- 완료/취소/0원/미수집 상태 테스트 추가

완료 기준:

- 선택 주와 비교 주가 모두 실제 수집 범위에 포함돼야 백분율이 표시된다.
- 수집 누락을 0원으로 표시하지 않는다.
- 500건 이상 주문도 페이지 누락 없이 집계된다.

### 2차 — 첫 화면 UI P0/P1

- 상단 중복 배너 축소
- 기간·상태·동기화 행동 통합
- KPI에 절대 차이와 비교값 추가
- 핵심 차트를 첫 화면 안으로 이동
- 동기화/화면 조회 워딩 분리
- 로딩, 마지막 데이터 유지, 오류 상태 개선

완료 기준:

- 1440×900에서 제목, 기간, 상태, KPI, 차트 시작 부분이 한 화면에 보인다.
- 320px 모바일에서 금액과 버튼이 겹치지 않는다.

### 3차 — 분석 행동 P1

- 지표 토글이 있는 일별 비교 차트
- 날짜 상세 드로어와 주문 연결
- 최대 증가/감소일 표시
- 메뉴 상위 10개 표, 필터, 검색, 정렬
- 메뉴 코드 우선 집계

### 4차 — 운영 확장 P2

- CSV/엑셀 다운로드
- 시간대별 매출
- 채널/POS 주문 출처별 비교
- 인건비 데이터와 결합한 매출 대비 인건비율
- 여러 사업장 합산 및 사업장 비교

인건비율과 순익은 권한과 산식이 다른 재무 데이터이므로 주간 매출 화면에 무조건 노출하지 않고 별도 권한이 있을 때만 제공한다.

## 7. 테스트 시나리오

1. 정상 완료 주와 전주가 모두 완결된 경우 KPI, 백분율, 일별 비교가 표시된다.
2. 선택 주 하루가 미수집이면 합계는 `수록된 매출`로 표시되고 증감과 인사이트는 숨겨진다.
3. 전주 매출이 0원이면 무한대 비율 대신 기준값 없음과 절대 차이가 표시된다.
4. 22시 이전 당일은 수집 대기, 22시 성공 후 1차 수집 완료로 바뀐다.
5. 마감 후 취소가 들어오면 재집계됨과 변경 금액이 표시된다.
6. 원주문과 일별 캐시 금액/건수가 다르면 불완전 상태가 된다.
7. 500건을 넘는 기간도 모든 페이지를 수집한다.
8. 같은 이름의 다른 메뉴 코드는 분리되고 이름이 바뀐 같은 코드는 연결된다.
9. 취소 주문은 완료 매출과 주문당 금액에 포함되지 않는다.
10. 동기화 실패 시 이전 확정값은 유지되고 오류와 재시도 행동이 표시된다.
11. 매출 권한이 없는 관리자는 금액, 주문 수, API 응답을 모두 볼 수 없다.
12. 모바일과 키보드 환경에서 기간 이동, 탭, 날짜 상세를 사용할 수 있다.

## 8. 최종 우선순위

이번 개발에서 먼저 해야 할 항목은 다음과 같다.

1. 수집 범위 기반의 `마감 완료` 판정
2. 동기화와 화면 조회 행동 분리
3. 상단 공간 축소와 KPI 절대 차이 추가
4. 일별 차트의 주문 수/주문당 금액 보조 정보
5. 날짜 상세와 원인 주문 연결
6. 메뉴 코드 기반 집계와 판매액·비중 확장

이 순서를 지키면 화면을 화려하게 만드는 작업보다 먼저 숫자에 대한 신뢰를 확보하고, 이후 차트와 운영 인사이트를 안전하게 확장할 수 있다.
