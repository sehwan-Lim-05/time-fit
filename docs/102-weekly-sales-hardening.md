# PR #1 주간 매출 보완 (2026-09-17)

기준: PR #1 `14c60e9`. 기존 주간 화면·최고관리자 조회 권한·유료 메뉴 이름별 합산 기준을 유지한다.

## 변경

- 주문은 고정된 결제 변경시간 `to`로 첫 페이지부터 끝까지 수집한다. 페이지별 자료와 다음 페이지를 DB staging/job에 저장하고, 실행 시간이 부족하면 다음 실행에서 이어받는다. 후속 페이지 실패·응답 오류 시 부분 자료를 게시하지 않는다.
- 원본 주문, 일별 완료 매출, 메뉴 수량 JSON, 완전성 체크포인트를 하나의 서비스 전용 DB 트랜잭션으로 게시한다. 매장 잠금, 오래된 게시 거절, 동일 매장의 사업장 충돌 차단을 적용한다.
- 매출에 `COMPLETED`만 포함한다. 취소 변경을 받으면 주문의 원래 KST 날짜도 다시 집계한다.
- 주간 조회는 단일 RPC에서 14일의 집계만 읽는다. 원본 주문 JSON·주문별 DB 페이지 조회는 제거했다. JSON은 DB 집계 열에 저장하며 공개 파일/CDN은 사용하지 않는다.
- 처음에는 완전성을 가정하지 않는다. 전체 이력을 자동 수집하고, 완료 후에만 무매출 날짜를 정상적인 0으로 비교한다. 이후 마지막 검증 체크포인트보다 1시간 앞부터 증분 수집하여 며칠 중단되어도 공백을 건너뛰지 않는다.
- 동기화 실패나 잘못된 메뉴 가격·수량·이름이 있으면 해당 비교를 보류한다. 정상 가격 0 메뉴는 기존 기준대로 제외한다.

## 적용 순서 / 검증 범위

운영 변경은 아직 하지 않았다. 코드·SQL을 검토/병합한 뒤 승인된 배포 절차로 `20260917000200`과 `20260917000300` 마이그레이션 및 API를 함께 적용해야 한다. API만 먼저 배포하면 새 RPC가 없어 조회가 실패한다.

기존 연결도 화면의 동기화 버튼 또는 예약 실행에서 체크포인트가 없으면 자동으로 전체 이력 수집을 시작한다. 강제 전체 재대조는 인증된 `/api/sync-sales?organizationId=…&mode=backfill` POST로 요청한다. 진행 중 작업이 있으면 우선 그 작업을 이어서 마치므로 강제 전체 재대조는 완료 후 다시 요청한다.

한 호출은 전체 45초 수집 예산을 매장별로 나누고 매장당 최대 8초/20페이지를 처리한다. `202 pending`은 완료가 아니며 다음 버튼 실행 또는 기존 매일 예약 실행에서 이어받는다. 브라우저 화면은 완료·수집 중을 구분한다. 상시 워커/더 잦은 예약 실행은 이번 변경에 포함하지 않아 큰 최초 이력은 여러 실행이 필요할 수 있다. 최종 집계 RPC의 DB 실행 시간은 별도 실측이 필요하다.

매장별 오류를 분리해 뒤 매장 처리를 계속한다. 실행권은 90초 후 만료되며 재시작 시 새 실행 토큰을 발급한다. 오래된 토큰, 완료 후 응답 유실, 이전 실행의 늦은 실패는 최신 연결 상태를 덮지 못한다. 페이지 체크포인트와 최종 게시/성공 상태는 각각 DB 트랜잭션으로 갱신한다.

비활성 중복 연결만 있으면 정상 매장 게시를 허용한다. 활성 중복 연결 또는 다른 사업장/소유권 미지정 원본 주문은 차단을 유지한다. 이는 사람의 소유권 확인과 명시적 이관이 필요한 상태이므로 임의로 활성 연결·원본 데이터를 삭제/이전하지 않는다.

단위/API 모킹 테스트, Vite 빌드, 격리 PostgreSQL 16 SQL 테스트로 검증한다. 운영 Toss API·운영 Supabase·Vercel 실제 지연은 이번 검증 범위 밖이다. 공급자 페이지 API 자체는 스냅샷/커서 계약이 없어 고정 `to`만으로 동시 변경에 대한 절대 무누락을 보장하지 않는다. 주기적인 전체 재대조/웹훅 보강은 후속이다.

기능 보완 후 검증 결과: Node 테스트 64개 통과, Vite 빌드 통과, PostgreSQL 16에서 `test/sql/resumable-sales-integration.sql` 통과. SQL 테스트는 페이지 중간 비공개, 실행권 중복/만료, 이전 토큰 오류 무시, 응답 유실 후 성공 유지, 최초 자동 전체 수집, 공백 체크포인트 복구, 인증정보 변경 시 수집 폐기, 비활성 중복 허용/활성 중복 차단을 검사한다. 토큰 교대는 순차 인터리빙 테스트이며 실제 동시 세션 부하/운영 성능 검증은 별도다. 기존에 발견한 보안 이슈 전체 해소는 사용자가 이번 작업 범위에서 제외했다.

읽기 지연을 줄이는 변경이다. 배치 집계는 아직 전체 이력을 재계산한다. dirty-date 증분 집계, webhook, JSON 파일 배포, 홈→상세 요청 공유 캐시는 이번 범위에 포함하지 않았다.
